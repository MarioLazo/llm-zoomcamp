# Peer Reviews — LLM Zoomcamp 2026, Project Attempt 2

Three assigned peer projects, reviewed for the course, written up here in
more depth than the platform's rubric form allows. Each review verifies
claims against the actual code — cloning the repo, running what could be
run, and reading the source behind rubric-mapping tables rather than
trusting them — because a checklist score only tells you *that* something
exists, not whether it actually holds up.

- [`knowledge-base-assistant-bot.md`](knowledge-base-assistant-bot.md) —
  a personal read-it-later assistant with grounded, cited answers over a
  Telegram bot. **21/21.**
- [`wc2026-rag.md`](wc2026-rag.md) — a World Cup 2026 news chatbot. **13/21.**
- [`nutrition-facts-chat.md`](nutrition-facts-chat.md) — a USDA nutrition-facts
  chatbot running entirely locally, no paid API required. **20/21.**

## What I learned across all three, in plain English

**The best projects say what they don't know, not just what they do.**
Every strong project here — and my own — was willing to publish a number
that complicates its own story instead of hiding it: an AI-judge score
labeled "not yet checked against a real human," a search result that didn't
improve the way "best practices" would predict, an evaluation labeled
"still needs to be run for real." That habit — flagging the gap instead of
staying quiet about it — turned out to be a better signal of project quality
than any single rubric line.

**A test only proves something if it actually touches the real system.**
The two most interesting bugs I found this cycle were both this exact
shape: a "monitoring" feature where the database tables existed but nothing
ever wrote to them, and an "LLM evaluation" table where neither compared
answer had actually been generated by the AI — one was raw pasted text, the
other was a template that cheated by reading the correct answer off the
answer key. Both were honestly disclosed in a code comment; neither was
disclosed clearly enough in the main write-up a reviewer would actually
read. The lesson: it's not enough for a test to exist and produce a number
— it has to run through the actual thing you're claiming to have tested.

**When you can check something with plain code instead of asking an AI to
judge it, that's usually the better choice.** The nutrition project's
strongest idea — checking whether the right *number* appears in an answer,
rather than asking an AI "does this look right?" — sidesteps a whole class
of problems where the AI grading the work has its own blind spots. It's a
narrower tool (only works when there's an objectively checkable answer),
but where it applies, it's more trustworthy than a subjective 1-5 score.

**Reproducibility is a spectrum, and it's worth being deliberate about
where you land on it.** One project needed no paid account anywhere and ran
entirely on the reviewer's own machine — the strongest position. The others
needed a metered or paid AI subscription just to run the answering step.
Neither choice is wrong, but it's a real, nameable tradeoff (free and local
vs. a stronger hosted model) that's worth stating on purpose rather than
leaving implicit.

**Test-set size is the difference between a result you can trust and one
you can't.** A 10-question test can make two very close options look
meaningfully different when they're actually within noise of each other. A
160-question test doesn't have that problem. This wasn't a formal course
requirement, but it was the single biggest driver of which projects'
conclusions I actually believed.

## Areas of improvement, across the board

- **Say what a test actually exercised, not just what it produced.** A
  README claiming "LLM evaluation" should mean the LLM was actually called
  — if a fast offline proxy metric was used instead (a reasonable choice!),
  say so in the same sentence as the number, not just in a code comment.
- **Finish or remove partial infrastructure — don't ship it half-wired.** A
  monitoring table that nothing writes to is worse than no monitoring
  table: it looks done on a skim and isn't.
- **Grow a test set before trusting a close result.** If two options are
  within a percentage point of each other on 10 questions, that's usually
  a sample-size problem, not a real finding — worth a bigger test before
  shipping a conclusion either way.
- **State reproducibility tradeoffs on purpose.** "This requires a paid API
  key" or "this needs 8GB of RAM" costs nothing to say up front and saves a
  reviewer real frustration discovering it mid-setup.
